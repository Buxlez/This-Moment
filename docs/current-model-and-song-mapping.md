# this moment：当前模型与歌曲映射机制

## 1. 文档目的

本文说明当前 Demo 如何把用户的一句话转换为最终可播放的歌曲卡片，重点解释“歌曲映射”到底发生在哪些阶段、每个阶段使用什么信息、哪些规则已经实现，以及哪些仍属于后续设计。

当前实现不是把“下雨”“通勤”“疲惫”等场景直接映射到固定歌单，也没有通过 BPM、调性、响度、音频向量或协同过滤直接召回歌曲。它采用的是一条分层链路：

```text
用户表达
  + 当前时间、天气和城市
  + 上一张卡片
  + 演示用户偏好
        ↓
确定性意图与环境处理
        ↓
DeepSeek 将语义转成音乐方向，并生成有序候选歌曲
        ↓
网易云搜索候选歌曲对应的真实平台实体
        ↓
名称匹配、历史排除、去重、可播校验、详情补全
        ↓
保留前 8 首真实可播歌曲，生成固定卡片
```

可以把它理解为三层映射：

1. **语义映射**：用户现在想要什么样的音乐；
2. **候选映射**：这个方向可能对应哪些“歌曲名 + 歌手名”；
3. **平台实体映射**：候选歌曲在网易云中对应哪个真实歌曲 ID，当前是否可以播放。

---

## 2. 第一层：用户表达映射为本轮意图

入口位于 `src/domain/intent.js`。当前使用少量可测试的确定性规则，将一轮请求分为四类。

| 意图 | 含义 | 示例 |
| --- | --- | --- |
| `cold_start` | 没有历史卡片，用户只提出宽泛请求 | “来点音乐” |
| `recommend` | 用户提出新的场景、状态或音乐需求 | “上班路上有点困，提神但别太吵” |
| `refine` | 基于上一张卡片调整某些维度 | “再安静一点” |
| `refresh` | 保持大致方向，更换歌曲 | “换一批” |

当前判断顺序为：

1. 有上一张卡片，并命中“换一批、再换、另一批”等表达，映射为 `refresh`；
2. 有上一张卡片，并命中“再、更、一点、保持、别太、稍微”等表达，映射为 `refine`；
3. 没有上一张卡片，且输入近似“来点音乐”，映射为 `cold_start`；
4. 其他情况映射为 `recommend`。

这一步只负责判断对话关系，不直接决定歌曲。

---

## 3. 第二层：环境信息合并

入口位于 `src/domain/environment.js`。

当前使用三个环境字段：

- `city`：城市；
- `localTime`：本地时间；
- `weather`：天气。

天气优先级为：

```text
用户原话中的明确天气
> 页面提交的天气
> “晴朗”默认值
```

例如页面当前选择“晴朗”，用户说“现在下雨，想听点松弛的”，最终天气会被解析为“下雨”。

当前能够从原话识别的天气词包括：

- 下雨：暴雨、大雨、小雨、下雨、雨天、雨夜；
- 雪天：下雪、雪天、雪夜；
- 寒冷：寒冷、很冷、降温、冷天；
- 高温：高温、炎热、闷热、很热；
- 多云：多云、阴天、阴沉；
- 晴朗：晴朗、晴天、天晴。

城市目前主要使用页面提交值；缺失时默认上海。时间使用页面提交值，缺失时使用当前时间。

## 4. 第三层：语义映射为音乐方向

当前音乐方向只使用三个核心维度：

| 字段 | 作用 | 示例 |
| --- | --- | --- |
| `atmosphere` | 整体听感和情绪空间 | 明亮、清晰、放松、有空间感 |
| `energy` | 音乐的推动力和刺激强度 | 中低、中等、中高但不过强 |
| `rhythm` | 节奏活跃度、稳定性和起伏 | 活跃、稳定、舒缓、低起伏 |

其中：

- 能量不等于速度；
- 天气不直接等于情绪；
- 场景不直接对应固定歌曲；
- 用户明确说出的上限和排除条件应当优先。

### 4.1 演示模式的显式规则

演示模式在 `llm.js` 的 `demoDirection()` 中使用明确规则。

| 用户语义 | 氛围 | 能量 | 节奏 |
| --- | --- | --- | --- |
| 困、提神、有精神 | 明亮、清晰 | 中高但不过强 | 活跃、稳定 |
| 累、放松、舒服、舒缓 | 放松、不过度低沉 | 中低 | 舒缓、稳定 |
| 夜景、氛围 | 都市、有空间感 | 中低至中等 | 流动、不过强 |
| 再轻松一点 | 继承上一轮并增加轻松、舒展 | 当前实现会做有限调整 | 主要继承 |

### 4.2 宽泛请求的时间映射

如果没有明确需求，本地确定性映射会根据时间产生基础方向。

| 时间 | 氛围 | 能量 | 节奏 |
| --- | --- | --- | --- |
| 05:00–09:00 | 清新、明亮 | 中高 | 轻快、稳定 |
| 09:00–17:00 | 自然、容易进入状态 | 中等 | 自然、稳定 |
| 17:00–22:00 | 放松、温和 | 中等 | 舒展、稳定 |
| 22:00–05:00 | 安静、克制 | 中低 | 舒缓、低起伏 |

天气再对基础方向做有限修正：

- 下雨：增加“松弛、有空间感”，能量调整为中低，增加低起伏；
- 晴朗：增加“轻松”；
- 雪天：整体改为安静、温暖、中低能量和低起伏。

### 4.3 真实模式由 DeepSeek 完成语义转译

真实模式不会直接调用 `demoDirection()`。程序会把以下上下文交给 DeepSeek：

- 本轮意图；
- 当前环境；
- 用户本轮原话，并明确标为最高优先级；
- 上一张卡片的音乐方向和歌曲；
- 最近需要排除的平台歌曲 ID；
- `user/taste.md` 中的演示偏好；
- `user/mood-rules.md` 中的情绪转译原则。

`mood-rules.md` 当前强调：

- 困或提神：提高能量和节奏活跃度，同时尊重“别太吵”等上限；
- 累或放松：降低能量和起伏，但不自动推断伤感；
- 专注：保持节奏稳定，减少情绪和编曲干扰；
- 雨天：可以更松弛、更有空间感，但用户本轮要求优先；
- 换一批：继承方向，排除上一张卡片；
- 微调：只改变用户点名的维度，其他方向继承。

DeepSeek 默认使用 `deepseek-v4-flash`，通过 OpenAI-compatible Chat Completions 接口调用。

## 5. 第四层：音乐方向映射为候选歌曲

这是当前歌曲映射最关键的一步。

DeepSeek 不只返回音乐方向，也会同时返回一个按推荐优先级排列的候选歌曲列表。输出结构为：

```json
{
  "intent": "recommend",
  "direction": {
    "atmosphere": ["明亮", "清晰"],
    "energy": "中高但不过强",
    "rhythm": ["活跃", "稳定"]
  },
  "title": "清醒一点，慢慢出发",
  "description": "两句话推荐语",
  "candidates": [
    { "title": "歌曲名", "artist": "歌手名" }
  ]
}
```

### 5.1 模型根据什么选择歌曲

模型选择候选时可使用以下信息：

1. 用户本轮的明确状态和要求；
2. 映射后的氛围、能量和节奏；
3. `taste.md` 中的演示品味；
4. 上一轮方向，用于微调或换一批；
5. 最近歌曲，用于降低重复；
6. 模型自身已学习到的歌曲与歌手知识。

当前 `taste.md` 包含的软偏好主要是：

- 有旋律、有空气感、适合长时间聆听；
- 中等能量为主，提神时允许中高能量；
- 中文约七成、英文约三成；
- 偏向华语创作歌手、独立流行、轻摇滚、城市民谣；
- 英文偏向 indie pop、dream pop、克制电子和氛围音乐；
- 避免连续高密度、高响度、强爆发；
- 避免同一卡片歌手过度集中。

这些偏好目前是 Prompt 中的自然语言指导，不是代码中的数值权重。

### 5.2 候选数量

最终卡片默认目标为 8 首。当前候选数量计算为：

```text
candidateTrackCount = min(targetTrackCount × 4, 40)
```

因此默认流程为：

```text
目标 8 首
→ DeepSeek 生成 32 首候选
→ 网易云逐首校验
→ 保留前 8 首真实可播歌曲
```

先生成更多候选，是因为部分候选可能出现以下问题：

- 网易云搜索不到；
- 搜索第一项不是目标歌曲；
- 歌曲名或歌手名不匹配；
- 当前没有可用播放地址；
- 与最近卡片重复；
- 候选之间指向同一个网易云歌曲 ID。

### 5.3 候选顺序的含义

模型输出顺序就是当前的基础排名。第 1 个候选应当比第 20 个候选更符合本轮方向。

系统不会在模型输出后重新计算“情绪相似度”，也不会进行随机打乱。即使网易云搜索并发执行，最终仍按照模型原始候选索引排序。

因此当前歌曲排序的本质是：

```text
DeepSeek 的语义排名
+ 真实音源过滤
= 最终卡片顺序
```

## 6. 第五层：候选歌曲映射为网易云实体

候选歌曲只是模型给出的文本，例如：

```json
{ "title": "小宇", "artist": "张震岳" }
```

系统需要将它转换成网易云中的真实实体：

```json
{
  "id": "网易云歌曲 ID",
  "title": "小宇",
  "artist": "张震岳",
  "album": "专辑名称",
  "coverUrl": "封面地址",
  "durationMs": 240000,
  "provider": "netease"
}
```

### 6.1 搜索方式

系统使用以下查询词搜索网易云：

```text
歌曲名 + 空格 + 歌手名
```

调用网易云 `/cloudsearch`，搜索类型为单曲，目前只取搜索结果第 1 项：

```text
type = 1
limit = 1
```

这意味着当前系统不会在搜索结果前 5 项或前 10 项中继续寻找更合适的版本。第一项匹配失败，该候选会直接被丢弃。

### 6.2 名称标准化

为了允许常见的标题差异，候选文本和网易云结果都会先标准化：

1. 转为小写；
2. 删除英文圆括号、中文圆括号和方括号中的内容；
3. 删除空格、标点和其他非字母数字字符。

例如：

```text
“小宇”              → “小宇”
“小宇 (Live)”       → “小宇”
“Wake Me Up!”       → “wakemeup”
“Wake Me Up [Live]” → “wakemeup”
```

### 6.3 歌曲名匹配

歌曲名满足以下任一情况即视为匹配：

- 标准化后完全相等；
- 候选标题包含网易云标题；
- 网易云标题包含候选标题。

因此“歌曲名”和“歌曲名（Live）”通常可以匹配，但标题完全不同会被拒绝。

### 6.4 歌手名匹配

如果候选和网易云结果都存在歌手名，则同样采用：

- 完全相等；
- 一方包含另一方。

例如：

- `Yellow / Coldplay` 对应 `Yellow / Coldplay`：接受；
- `Yellow / Coldplay` 对应 `Yellow / Katherine Ho`：拒绝；
- 多歌手合作曲中，一方字符串包含另一方时可能接受。

如果候选或平台结果缺少歌手名，当前实现不会因为歌手字段缺失直接拒绝。这是一种提高召回率的宽松策略，也意味着少数情况下存在误匹配风险。

## 7. 第六层：排除、去重和可播校验

名称匹配通过后，候选仍需依次通过以下检查。

### 7.1 历史排除

当前管线读取同一会话最近两张卡片，将其中所有网易云歌曲 ID 加入排除集合。

因此新卡片不会再次接受最近两张卡片中已经出现的同一平台歌曲 ID。当前实际实现不是“最近 24 小时”，而是“最近两张卡片”。

### 7.2 卡片内去重

同一张卡片内使用网易云歌曲 ID 去重。即使两个不同候选文本最终搜索到同一个平台 ID，也只保留一次。

### 7.3 可播放校验

系统调用网易云 `/song/url/v1`，并使用配置的音质等级，默认是 `standard`。

只有接口返回非空播放 URL，歌曲才被视为当前可播放。常见失败原因包括：

- 版权或区域限制；
- 当前账号无权限；
- 会员音质或歌曲权限问题；
- 网易云接口暂时限流；
- 播放地址临时不可用。

不可播放的候选不会进入卡片。

### 7.4 详情补全

只有确认可播放之后，系统才调用 `/song/detail` 获取：

- 专辑名；
- 封面；
- 时长；
- 规范歌曲名；
- 规范歌手名。

先检查可播、再获取详情，可以减少无效候选产生的额外接口请求。

## 8. 并发、顺序与停止条件

默认校验并发数为 2。

```text
候选 1 ─┐
         ├─ 并发搜索与校验
候选 2 ─┘
候选 3、4……随后继续
```

并发只用于缩短等待时间，不改变模型排名。每首通过的歌曲会保留原始候选索引，最后按照索引从小到大排序。

当已找到目标数量时，校验任务会尽快停止继续领取新候选。并发任务可能已经在处理少量候选，但最终结果仍会截取前 8 首。

如果 32 首候选最终只有 5 首可确认播放，系统会返回这 5 首，并显示：

> 暂时只找到 5 首可确认播放的歌曲，已如实保留。

系统不会：

- 第二次调用模型补歌；
- 使用其他音乐平台补齐；
- 用演示歌曲冒充网易云结果；
- 为了凑满数量而保留不可播放歌曲。

---

## 9. 网易云请求稳定性处理

当前音源层包含以下稳定性措施：

| 类型 | 当前策略 |
| --- | --- |
| 请求节流 | 网易云请求启动间隔至少约 350 ms |
| 搜索缓存 | 10 分钟 |
| 可播状态缓存 | 2 分钟 |
| 歌曲详情缓存 | 30 分钟 |
| 相同请求合并 | 同一个缓存键的并发请求共享一次上游调用 |
| 限流重试 | HTTP 405 或 429 最多重试 2 次 |
| 退避时间 | 约 700 ms、1400 ms |
| 单次超时 | 默认 8 秒 |

缓存只影响请求效率，不改变歌曲排序。

## 10. 一个完整映射示例

用户输入：

> 上班路上有点困，想提神但别太吵。

页面环境：

```json
{
  "city": "上海",
  "weather": "晴朗",
  "localTime": "2026-08-06T08:20:00+08:00"
}
```

### 第一步：意图

没有上一张卡片，输入不是单纯的“来点音乐”，因此：

```text
intent = recommend
```

### 第二步：语义方向

模型需要综合理解：

- “上班路上”：通勤场景；
- “有点困”：需要提高推动力；
- “提神”：能量和节奏应当上调；
- “别太吵”：形成刺激强度上限；
- 早晨和晴朗：只能作为辅助信息，不能覆盖用户要求。

可能得到：

```json
{
  "atmosphere": ["明亮", "清晰"],
  "energy": "中高但不过强",
  "rhythm": ["活跃", "稳定"]
}
```

### 第三步：模型候选

DeepSeek 根据方向、演示品味和自身歌曲知识，返回 32 个按匹配度排列的“歌曲名 + 歌手名”。

这里的 32 首仍然只是文本候选，不代表已经找到真实音源。

### 第四步：逐首映射网易云

假设第一个候选是：

```json
{ "title": "Wake Me Up", "artist": "Avicii" }
```

系统执行：

1. 搜索 `Wake Me Up Avicii`；
2. 取得网易云第一条单曲结果；
3. 标准化歌曲名和歌手名；
4. 检查标题、歌手是否匹配；
5. 检查歌曲 ID 是否出现在最近两张卡片；
6. 检查本卡片是否已有相同歌曲 ID；
7. 请求播放 URL；
8. 可播放后获取封面、专辑和时长；
9. 记录它在模型候选中的原始位置。

### 第五步：形成卡片

系统继续检查后续候选，直到得到 8 首真实可播放歌曲，或者所有候选已经用完。最终卡片顺序保持模型候选的相对顺序。

## 11. 当前机制没有做什么

为了避免把设计目标误认为现有能力，需要明确当前没有实现以下内容：

### 11.1 没有音频特征匹配

当前没有读取或计算：

- BPM；
- 调性；
- 响度；
- 能量值；
- valence；
- danceability；
- 音频 embedding；
- 波形或频谱特征。

“能量、节奏、氛围”到歌曲的对应关系，主要来自 DeepSeek 对歌曲的知识，而不是对音频文件的实际分析。

### 11.2 没有向量数据库或语义检索库

当前没有建立歌曲标签库、歌词向量库或场景 embedding，因此不存在“把用户表达向量化，再从百万首歌曲中找最近邻”的过程。

### 11.3 没有平台推荐模型

网易云只承担搜索、实体确认和播放校验。系统没有调用网易云的私人 FM、猜你喜欢或推荐歌单能力。

### 11.4 没有真实数值加权排序

设计文档中曾规划根据偏好、语言、历史和歌手集中度进行软权重排序，但当前代码没有实现该数值模型。

当前排序仍然是：

```text
模型候选顺序 → 删除无效项 → 保持剩余项相对顺序
```

### 11.5 结构化语义字段仍较少

当前卡片只持久化：

- 意图；
- 环境；
- 氛围、能量、节奏；
- 推荐语；
- 歌曲结果。

原设计中的 `scene`、`direction_source`、语言、人声、曲风、年代、乐器、排除项等完整结构还没有全部进入实际 Schema 和数据库。

---

## 12. 当前方案的优点与风险

### 优点

1. 可以理解“提神但别太吵”这类包含上下限的自然语言；
2. 不需要维护庞大的人工“场景—歌曲”规则表；
3. 音源必须经过真实平台验证，不会直接相信模型；
4. 模型与音乐平台职责清晰；
5. 不足 8 首时如实返回，产品行为比较诚实；
6. 卡片顺序稳定，保存后不会因重启或偏好变化而改变。

### 风险

1. 模型可能记错歌曲名或歌手；
2. 网易云只检查搜索第一项，可能错过后面的正确结果；
3. 包含关系匹配对某些短标题可能过于宽松；
4. 缺少歌手字段时仍可通过，存在少量误匹配风险；
5. 没有真实音频特征，模型认为“安静”的歌不一定在声学上真的低能量；
6. 偏好目前是 Prompt 文本，没有可解释的数值权重；
7. 最近去重当前只看两张卡片，不是按 24 小时或完整播放历史计算。

## 13. 推荐的下一阶段映射升级

如果继续提高歌曲映射的准确度，可以按以下顺序演进。

### 阶段一：加强网易云实体匹配

- 搜索前 5–10 项，而不是只取第一项；
- 对歌曲名、歌手名分别计算匹配分；
- 显式识别 Live、翻唱、伴奏、Remix、纯音乐等版本；
- 用户未要求特殊版本时优先录音室原版；
- 为短标题设置更严格的完全匹配规则。

这是成本最低、对当前效果提升最直接的一步。

### 阶段二：把用户约束结构化

将模型输出扩展为：

```json
{
  "scene": {},
  "direction_source": "user_translation | inherited_context | system_default | mixed",
  "direction": {},
  "constraints": {
    "languages": [],
    "vocals": [],
    "genres": [],
    "artists": [],
    "eras": [],
    "instruments": [],
    "avoid": []
  }
}
```

这样“不要中文歌”“多一点女声”“不要现场版”等要求就可以在候选校验阶段成为硬过滤条件，而不只是 Prompt 提示。

### 阶段三：引入可解释的重排分数

可以在真实可播候选上计算：

```text
最终分数
= 模型原始排名分
+ 用户明确偏好匹配分
+ 长期品味匹配分
+ 新鲜度分
- 最近重复惩罚
- 歌手集中惩罚
- 版本不匹配惩罚
```

用户明确约束仍然应当作为硬过滤，而不是允许被其他分数抵消。

### 阶段四：增加真实音乐特征

如果能够获得可靠的歌曲音频特征或自建分析结果，可以将“能量、节奏、氛围”映射到：

- BPM 区间；
- 动态范围；
- 平均响度；
- 节奏稳定性；
- 人声比例；
- 编曲密度；
- 情绪和声学 embedding。

这时系统才真正具备“语义方向 + 声学事实”的双重匹配，而不是主要依赖模型对歌曲的记忆。

---

## 14. 一句话总结

当前歌曲映射不是固定场景歌单，也不是音频向量推荐，而是：

> 先让 DeepSeek 根据用户语义、环境、上一轮和演示偏好生成一个有序的歌曲候选列表，再将每个候选映射到网易云真实歌曲 ID，经过名称匹配、历史排除、去重、可播性检查和元数据补全后，保留顺序最靠前的 8 首真实可播歌曲。
