# this moment MVP 混合转译设计规格

> 日期：2026-08-04  
> 状态：用户已确认，待书面规格终审  
> 产品形态：本地单用户桌面网页 Demo  
> 产品依据：`新版prd.docx` 中“用户主动触发音乐推荐（基线 5.2）”  
> 技术底座：[bingyanglu/Claudio-FM](https://github.com/bingyanglu/Claudio-FM)  
> 锁定基线：`4939b1adc5ddc5ed1289a1e93cd0235b98634abe`

## 1. 设计结论

本 MVP 使用“确定性规则 + 大模型转译 + 音源事实校验”的混合转译方案：

```text
用户本轮表达
+ 上一轮有效字段
+ 自动时间、定位和天气
+ 系统默认映射
+ 用户偏好与近期播放
        ↓
字段优先级合并
        ↓
DeepSeek 一次输出
场景拆解 + 氛围/能量/节奏 + 候选歌曲 + 推荐语
        ↓
偏好加权 + 网易云检索 + 可播校验 + 去重
        ↓
默认 8 首卡片（可配置到 20 首）
        ↓
两句推荐语 TTS + 用户点击播放
```

保留 Claudio-FM 的 Node.js、Express、WebSocket、SQLite、DeepSeek/OpenAI-compatible SDK、NeteaseCloudMusicApi、二维码登录、火山引擎 TTS 和 HTML Audio 播放器。不引入 React、向量数据库、独立 Worker 或新的音乐推荐平台。

## 2. 新版 PRD 的解读边界

`新版prd.docx` 前半部仍保留历史方案，包括车外拍照、端侧 VLM、3 首歌曲、默认自动播放和系统主动推荐。本 MVP 以第 19 页开始的“用户主动触发音乐推荐（基线 5.2）”为唯一产品依据。

本 MVP 不包含：

- 车外摄像头拍照和端侧 VLM；
- 天气关怀、跨省出游、反常时段和节假日主动推荐；
- 车机挂档、车速、座椅或导航信号；
- QQ 音乐、酷狗和多音源切换；
- AI 电台串场、逐首介绍和无限续播；
- 真实长期用户画像学习；
- 移动端页面。

## 3. MVP 要验证的问题

1. 系统能把“提神但别太吵”类模糊表达稳定转译为氛围、能量和节奏。
2. 用户本轮明确要求始终高于天气、时间和默认偏好。
3. “来点音乐”类宽泛请求能根据时间和天气给出可重现的默认方向。
4. “再安静一点”只修改相关字段，不丢失上一轮其他条件。
5. 最终歌曲真实存在于网易云并且当前可播放。
6. `taste.md` 能影响候选排序，但不覆盖用户明确条件。
7. 推荐语可以通过 TTS 播放，TTS 失败不影响歌曲卡片。

## 4. 用户范围路由

### 4.1 进入模糊推荐流程

首轮请求满足以下任一条时进入：

- 含空间、受众或行为目的的场景表达；
- 含困、累、心烦、想放空或想专注等状态感受；
- 含“舒服一点”“热闹但别太吵”等模糊音乐需求；
- 只有“给我推荐点歌”“来点音乐”等宽泛意图；
- 场景表达和明确音乐条件混合出现，例如“适合下雨天听的周杰伦的歌”。

### 4.2 不进入本流程

只含明确歌手、歌曲、专辑、曲风、语言、年代、人声或乐器的点播、搜索或事实问答不进入模糊推荐。正式车机产品应路由给已有媒体 Agent；本地 MVP 没有该 Agent，因此显示“本 Demo 专注场景、状态和模糊音乐推荐”，不伪造点播结果。

Scope Router 使用可测试的明确意图规则识别纯点播、搜索和事实问答。当一条请求同时像模糊推荐和明确点播，或无法可靠判断时，默认进入混合转译流程，并将明确音乐条件作为硬约束。

## 5. 信息模型与字段优先级

### 5.1 环境字段

- 时间：读取电脑当前时间；
- 天气：优先自动定位后查询 Open-Meteo；
- 城市：用户原话中明确出现时使用，无反向地理编码时可保持为空；
- 所有环境字段都允许为空。

环境字段优先级：

```text
用户本轮原话中的明确描述
> 用户本轮手动选择的天气
> 最新有效上下文
> 浏览器定位和天气服务
> 天气失败时的“晴朗”默认值
```

### 5.2 用户语义字段

所有字段允许为空：

- `space`：车内、家中、办公室、户外等；
- `audience`：宝宝、儿童、情侣、家人、朋友等；
- `activity`：通勤、驾驶、乘车、等待、出游、工作、休息、聚会等；
- `state`：困、累、心烦、想放空、想专注等；
- `fuzzy_request`：提神但别太吵、舒服但别太伤感等；
- `explicit_constraints`：用户明确说出的语言、曲风、人声、乐器、年代、歌手和排除条件。

用户语义字段独立生效，优先级为：

```text
用户本轮表达
> 最新有效上下文
> 系统默认映射
> 保持为空或不限定
```

用户本轮未提到空间环境时，按新 PRD 默认为“车内”。不得默认填入“独自一人”“长途旅行”或其他用户未表达的信息。

## 6. 混合转译规则

### 6.1 只转译三个音乐方向

模糊语义只转译：

| 字段 | 定义 | 取值形式 |
|---|---|---|
| 氛围 `atmosphere` | 音乐整体带来的听感 | 1–3 个短语，如明亮清晰、开阔、温柔治愈 |
| 能量 `energy` | 整体情绪推动力和刺激强度 | 低、中低、中、中高、高 |
| 节奏 `rhythm` | 速度、律动和稳定程度 | 1–3 个短语，如强劲律动、持续平稳、低起伏 |

三者不互相替代。能量不等于速度。场景只形成方向，不直接对应固定歌曲或歌单。

曲风、语言、人声、乐器、年代和歌手不从模糊场景中推断。它们只能来自用户明确表达、已确认的上下文或宽泛请求的系统默认。

### 6.2 宽泛请求的确定性时间映射

| 时间段 | 基础氛围 | 基础能量 | 基础节奏 |
|---|---|---|---|
| 05:00–09:00 | 明亮清晰、清爽 | 中高 | 活跃、鼓点利落 |
| 09:00–17:00 | 自然通透 | 中 | 平稳舒展、律动规整 |
| 17:00–22:00 | 温柔治愈 | 中 | 轻快流动、起伏柔和 |
| 22:00–05:00 | 清冷克制 | 中低 | 舒缓平缓、低起伏 |

该表只在用户没有提供场景、状态、模糊需求，且没有最新有效方向时使用。

### 6.3 天气调整

自动天气支持新 PRD 的全量内部类型：晴朗、多云/阴天、小雨、大雨、高温、寒冷、雪、大雾、沙尘/大风、未知。用户手动兜底仅显示六个简化选项：晴朗、多云、小雨、大雨、炎热、寒冷。

| 天气 | 调整 |
|---|---|
| 晴朗 | 偏向明亮鲜活，能量上调 1 档 |
| 多云/阴天 | 偏向温润松弛，能量和节奏维持 |
| 小雨 | 偏向温润、松弛和空间感，能量下调 1 档 |
| 大雨 | 偏向沉静安抚，能量下调 1 档，节奏限制为平缓低起伏 |
| 高温 | 偏向清爽轻盈，过滤厚重压抑编曲 |
| 寒冷 | 偏向温柔治愈和温暖，能量与节奏维持 |
| 雪 | 偏向静谧温暖，能量下调 1 档 |
| 大雾 | 偏向清冷克制，能量下调 1 档，禁用强劲奔放律动 |
| 沙尘/大风 | 偏向清爽清晰，能量下调 1 档，禁用强劲奔放律动 |
| 未知 | 不调整 |

天气只在宽泛请求或本轮相关字段缺失时补充，不覆盖用户明确要求。用户说“下雨但想听热闹一点”时，“热闹”优先。

### 6.4 宽泛请求的其他默认

- 无已知偏好时，语言默认中文:英文 = 3:2；
- 人声默认混合男声和女声；
- 曲风、乐器、年代和歌手不限定；
- 时间和天气都缺失时，使用“主流流行、多年代、中英文 3:2、混合男女声”兜底。

能量调整始终限制在五档内，不得低于“低”或高于“高”。

## 7. 用户偏好的新职责

`taste.md` 从“硬性默认方向”改为“候选生成和排序的软偏好”：

- 用户本轮明确要求始终高于 `taste.md`；
- 有场景或模糊需求时，`taste.md` 只在符合本轮方向的候选中加权；
- 宽泛请求时，`taste.md` 影响可以更强；
- 用户明确说“不要中文歌”时，中文偏好失效；
- `taste.md` 不自动被播放历史改写；
- `routines.md` 不再定义冷启动方向，新 PRD 的确定性时间表是唯一冷启动时间规则。

无真实收藏、关注歌手或常听曲风接口时，本地 `taste.md` 代表一个明确的演示用户偏好。

## 8. 连续调整与结构化记忆

连续调整不再只依赖最近对话让模型自行猜测。每轮保存实际生效的字段和来源。

示例：

```text
上一轮：
氛围 = 明亮清晰、清爽
能量 = 中高
节奏 = 活跃、鼓点利落、强度受控
排除 = 嘈杂、刺耳、炸裂编曲

本轮：“再安静一点”

结果：
氛围 = 继承
能量 = 降低一档
节奏 = 降低活跃度和起伏
明确条件 = 继承
歌曲 = 排除上一张卡片
```

支持的连续意图：

| 用户表达 | 处理 |
|---|---|
| 再安静一点 | 降低能量和节奏，其他字段继承 |
| 再提神一点，但别太炸 | 提高能量，新增强度上限 |
| 别这么伤感 | 更新氛围排除项 |
| 不要中文歌 | 更新语言条件 |
| 多一点女声 | 更新人声条件 |
| 换一批 / 推荐点别的 | 方向完全继承，排除上一张卡片和近期歌曲 |

用户切换为明确点播、搜索或事实问答时，退出连续模糊推荐。

## 9. 统一 DeepSeek Prompt

### 9.1 调用策略

每轮正常推荐只调用一次 DeepSeek，一次返回：

1. 请求意图；
2. 场景、状态和模糊需求拆解；
3. 氛围、能量和节奏；
4. 明确音乐条件和排除项；
5. 候选歌曲；
6. 符合新 PRD 的两句推荐语。

结构或文案校验失败时，允许一次“仅修复 JSON/字段/推荐语，不改变方向和候选歌曲”的修复调用。这不属于第二轮补歌。修复仍失败时，本轮失败。

### 9.2 Prompt 四个组成块

```text
A. 固定角色与边界
B. 本轮已确认输入
C. PRD 转译与推荐语规则
D. 严格 JSON 输出格式
```

#### A. 固定角色与边界

```text
你是私人音乐推荐编辑。
你只把场景、状态和模糊音乐需求转译为氛围、能量和节奏。
不得在没有依据时推断曲风、语言、人声、乐器、年代或歌手。
用户本轮明确表达优先于历史、天气、时间和偏好。
不得因为夜晚推断疲惫，不得因为下雨推断伤感。
场景只形成音乐方向，不直接对应固定歌单。
```

#### B. 本轮已确认输入

运行时用 JSON 注入，不使用拼接的自然语言标题冒充数据：

```json
{
  "environment": {
    "time": "08:30",
    "weather": "小雨",
    "temperature_c": 27,
    "apparent_temperature_c": 30,
    "city": null
  },
  "user_input": "上班路上有点困，想提神但别太吵",
  "previous_effective_context": null,
  "explicit_constraints": {},
  "taste_profile": "偏爱旋律感和空气感，以华语独立流行为主",
  "recent_tracks": [],
  "target_track_count": 8,
  "candidate_track_count": 16
}
```

#### C. PRD 规则

注入本规格第 4–8 节的压缩机器版本，以及新 PRD 6.4.1 推荐语规则：

```text
根据已确认的环境、用户原话和本轮音乐方向生成推荐语。
不得自行决定或补充音乐方向。
推荐语必须是两句话，去除首尾空白后共 45–70 个 Unicode 字符，中文标点、数字和拉丁字母均计入长度，不按 UTF-8 字节数计算。
第一句自然带出一个已确认的真实环境信息，并回应用户明确需求。
第二句说明本轮真实音乐方向如何回应用户此刻需求。
字段为空时自然省略，不得编造城市、天气、状态或偏好。
```

#### D. JSON 输出契约

```json
{
  "schema_version": "1.0",
  "intent": "first_semantic | cold_start | refine | refresh",
  "direction_source": "user_translation | inherited_context | system_default | mixed",
  "scene": {
    "space": "string or null",
    "audience": ["string"],
    "activity": ["string"],
    "state": ["string"],
    "fuzzy_request": ["string"]
  },
  "direction": {
    "atmosphere": ["string"],
    "energy": "low | medium_low | medium | medium_high | high",
    "rhythm": ["string"]
  },
  "constraints": {
    "languages": ["string"],
    "vocals": ["string"],
    "genres": ["string"],
    "artists": ["string"],
    "instruments": ["string"],
    "eras": ["string"],
    "avoid": ["string"]
  },
  "candidates": ["歌曲名 - 歌手名"],
  "say": "两句话推荐语",
  "reason": "内部简短说明"
}
```

模型只返回一个 JSON 对象，不得返回 Markdown、代码围栏、解释或思维链。`reason` 仅用于本地调试，不展示给用户，日志中不保存模型隐藏推理。

## 10. 候选歌曲、偏好加权和网易云校验

### 10.1 数量

- `target_track_count` 默认为 8；
- 配置范围为 1–20；
- `candidate_track_count = min(target_track_count × 2, 40)`；
- 默认 8 首时，DeepSeek 生成约 16 首候选；
- 不执行第二轮模型补选；
- 校验后不足目标数量时，返回实际可播数量。

### 10.2 校验顺序

1. 用“歌名 + 歌手”搜索网易云；
2. 核对歌名和歌手；
3. 获取平台歌曲 ID、封面、专辑、时长等元数据；
4. 确认当前可播放；
5. 排除同一卡片重复歌曲；
6. 排除近期 24 小时进入队列的歌曲；
7. `refresh` 时排除上一张卡片的全部歌曲；
8. 限制同一主歌手连续出现不超过 2 首。

搜索并发上限为 4。不使用 `yt-dlp`、QQ 音乐、酷狗或假数据补齐。

### 10.3 带权选择

不做无差别纯随机。DeepSeek 必须将 `candidates` 按本轮方向与 `taste.md` 的综合匹配度从高到低排列。验证后的候选权重以模型排名为基础，只用网易云元数据中可确认的歌手、语言线索和历史记录修正；不伪造网易云未提供的曲风或氛围标签。对所有可播候选计算软权重：

- 符合 `taste.md` 的歌曲加权；
- 用户明确条件是必须过滤条件，不是可选加权；
- 近期歌曲和上一张卡片权重为 0；
- 过度集中的歌手降权；
- 从合格集合中做无放回带权抽样，生成卡片固定顺序。

测试通过注入可预测随机数生成器保证可重现。卡片一旦保存，不因后续偏好变化或重启改变顺序。

## 11. 推荐语与 TTS

- 推荐语由统一 DeepSeek 调用生成；
- 必须是两句，去除首尾空白后共 45–70 个 Unicode 字符，标点、数字和拉丁字母计入长度；
- 只使用已确认的环境、用户原话和生效方向；
- 不展示模型内部推理；
- 卡片成功保存后，异步调用火山引擎合成 `say`；
- 以“文本 + 音色 + 语速”的 SHA-256 作为 MP3 缓存键；
- 合成完成只更新“播放推荐语”按钮，不自动播放；
- “播放全部”默认先播推荐语，再从第 1 首开始；
- TTS 失败不影响文字、卡片和歌曲播放。

## 12. 桌面页面设计边界

页面只优化桌面宽度，目标范围 1024–1600 px，不设计独立手机布局。

页面包含：

1. `this moment` 标题和网易云登录状态；
2. 自动环境行：时间、天气、温度、体感温度，城市可为空；
3. “手动调整”展开的六个天气选项；
4. 自然语言输入框和推荐按钮；
5. 理解、候选、校验、整理四阶段进度；
6. 按时间倒序的推荐卡片；
7. 固定底部播放器。

每张卡片默认显示：

- 两句推荐语；
- 本轮实际天气或手动天气；
- 实际歌曲数量和网易云来源；
- 默认 8 首歌曲，实际有多少显示多少；
- 每首的封面、歌名、歌手和播放状态；
- “播放推荐语”“播放全部”“换一批”；
- 数量不足和 TTS 失败的非阻断提示。

氛围、能量、节奏默认不占用卡片主视觉，放在“查看推荐依据”折叠区。折叠区只展示结构化结果和字段来源，不展示 Prompt、`reason` 或思维链。

播放器支持单曲、播放全部、暂停、继续、上一首、下一首、进度拖动和队列自动续播。

## 13. 系统组件边界

| 组件 | 职责 | 不负责 |
|---|---|---|
| Scope Router | 判断首轮是否进入模糊推荐，识别连续调整 | 不选歌 |
| Environment Resolver | 时间、定位、天气、手动兜底和优先级 | 不推断用户情绪 |
| Default Mapper | 宽泛请求的时间基础值、天气调整和默认条件 | 不处理复杂自然语言 |
| Context Merger | 字段级优先级、继承、来源和上一张卡片 | 不调用外部服务 |
| Prompt Builder | 组装角色、确认输入、规则和 JSON 契约 | 不在代码里重新解释模型输出 |
| LLM Adapter | 调用 DeepSeek、超时、JSON 校验和一次修复 | 不检索歌曲 |
| Preference Ranker | 根据 `taste.md` 和历史产生软权重 | 不覆盖用户硬条件 |
| Netease Resolver | 搜索、匹配、可播校验和元数据 | 不生成推荐方向 |
| Card Repository | 保存字段、来源、卡片和固定歌曲顺序 | 不修改已保存卡片 |
| TTS Adapter | 合成并缓存 `say` | 不阻断卡片返回 |
| Desktop PWA | 环境、输入、进度、卡片、依据折叠区和播放器 | 不执行推荐规则 |

## 14. SQLite 数据设计

保留 Claudio-FM 原有的 `messages`、`plays` 和 `prefs`，新增结构化转译和卡片数据。

### 14.1 `turns`

每次请求保存：

- 用户原话；
- 意图和方向来源；
- 生效环境及字段来源；
- 生效场景字段；
- 氛围、能量、节奏；
- 明确音乐条件和排除项；
- 请求状态和错误类型；
- 创建时间。

结构化字段可以 JSON 形式保存于本地 SQLite，但服务层必须对输入和输出做 schema 校验。

### 14.2 `cards`

每张卡片保存：

- 对应 turn ID；
- 推荐语；
- 目标数量、实际数量和数量不足提示；
- TTS 状态、缓存文件和脱敏错误；
- 创建时间。

### 14.3 `card_tracks`

每首保存：

- 卡片 ID 和固定顺序；
- 网易云歌曲 ID；
- 歌名、歌手、专辑、封面和时长；
- 偏好权重和最终选中来源；
- 不长期保存网易云临时播放 URL。

## 15. HTTP 和 WebSocket 契约

### 15.1 HTTP

- `POST /api/environment/resolve`：根据浏览器经纬度查询天气，不保存精确坐标；
- `GET /api/weather-presets`：返回六个手动兜底选项；
- `POST /api/chat`：提交用户原话、环境快照和手动天气覆盖；
- `GET /api/cards`：返回历史卡片；
- `GET /api/cards/:id`：返回固定卡片、歌曲和可展开的推荐依据；
- `POST /api/cards/:id/tts/retry`：重试推荐语 TTS；
- `POST /api/playback/resolve`：按网易云歌曲 ID 刷新临时播放地址；
- `GET /api/tts/:filename`：安全返回哈希命名的本地 MP3；
- `GET /api/now` 和 `GET /api/next`：保留 Claudio 播放状态契约。

`POST /api/chat` 示例：

```json
{
  "message": "上班路上有点困，想提神但别太吵",
  "environment": {
    "time": "2026-08-04T08:30:00+08:00",
    "weather_id": "light_rain",
    "temperature_c": 27,
    "apparent_temperature_c": 30,
    "city": null,
    "source": "auto"
  },
  "manual_weather_override": null
}
```

### 15.2 WebSocket `/stream`

- `recommendation-status`：`understanding`、`translating`、`searching`、`validating`、`composing`；
- `recommendation-ready`：完整卡片已保存；
- `tts-ready`：推荐语 MP3 已就绪；
- `tts-failed`：TTS 失败但卡片可用；
- `control`：播放、暂停、上一首和下一首。

## 16. 端到端数据流

1. 页面启动后读取电脑当前时间。
2. 页面请求浏览器定位权限。
3. 同意后，只将经纬度传给本地服务查询 Open-Meteo；精确坐标不写入 SQLite 或日志。
4. 拒绝或天气失败后，页面显示六个手动选项，默认晴朗。
5. 用户提交最多 500 个字符的原话。
6. Scope Router 判断是否进入模糊推荐和是否属于连续调整。
7. Environment Resolver 和 Context Merger 生成已确认输入及每个字段来源。
8. 宽泛请求先执行 Default Mapper；其他请求保持未表达的音乐条件为空。
9. Prompt Builder 组装四个 Prompt 块，LLM Adapter 调用 DeepSeek。
10. 输出通过 JSON、枚举、句数、字符数和候选数量校验，必要时修复一次。
11. Netease Resolver 并发搜索、匹配、去重并验证可播。
12. Preference Ranker 执行硬条件过滤和软偏好加权，无放回抽取目标数量。
13. 同一事务内保存 turn、card 和固定顺序的 tracks；保存失败不返回成功卡片。
14. 服务返回卡片，随后异步生成 TTS 并通过 WebSocket 更新。
15. 用户播放某首歌前，服务按 ID 刷新一次网易云临时播放 URL。

### 16.1 性能和进度反馈

新 PRD 历史章节中的“结果卡完全显示 ≤ 4 秒”作为未来车机生产目标，不作为本地 MVP 的硬性验收门槛。MVP 需记录端到端耗时，页面提交后 300 ms 内显示首个进度状态，TTS 始终异步生成。完成真实 DeepSeek 和网易云基准测试后，再将结果卡耗时转为可量化优化目标。

## 17. 错误与降级

| 情况 | MVP 行为 |
|---|---|
| 定位权限被拒绝 | 显示六个手动天气，默认晴朗 |
| Open-Meteo 失败 | 使用手动天气，不阻断推荐 |
| 城市未知 | 城市保持为空，推荐语自然省略 |
| 请求属于明确点播/搜索 | 说明本 Demo 范围，不伪造结果 |
| DeepSeek 未配置 | 显示配置说明，不返回假推荐 |
| 模型请求失败 | 显示重试入口，不保存失败卡片 |
| JSON/字段/推荐语首次无效 | 只修复一次，不重新选歌 |
| 修复仍失败 | 本轮失败，不从普通文本猜测结果 |
| 网易云 sidecar 未启动 | 启动脚本提示并阻止推荐 |
| 网易云未登录 | 提供二维码登录入口 |
| 可播数量少于目标 | 返回实际数量并显示非阻断提示 |
| 没有任何可播歌曲 | 本轮失败，不保存空卡片 |
| 单曲 URL 过期 | 播放前刷新一次，仍失败则跳过 |
| TTS 失败 | 保留文字、卡片和音乐播放 |
| WebSocket 中断 | 重连后通过卡片接口恢复状态 |
| SQLite 保存失败 | 不返回未持久化的成功卡片 |

## 18. 安全和隐私

- `.env`、网易云 Cookie、SQLite、TTS 缓存和日志不得提交；
- 精确经纬度只用于当次天气查询，不写入数据库和日志；
- 日志不得打印完整 API Key、Cookie 或临时播放 URL；
- 用户输入最多 500 个字符；
- 模型输出必须做 schema 校验，不直接作为 HTML；
- 页面对服务端文本使用 `textContent`，不注入未净化 HTML；
- TTS 文件名只接受 64 位小写十六进制哈希加 `.mp3`；
- 播放 URL 不长期保存；
- 本地服务默认只监听 loopback，不开放公网访问。
